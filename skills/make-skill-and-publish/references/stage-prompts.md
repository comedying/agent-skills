# 分阶段提示词模板

本文件有两个用途：记录这套流程的原始提示词（来源：B 站「木子不写代码」视频截图，4 张），
以及给出按最新 Agent Skills 规范修订后、可直接复制的提示词模板。

按需使用：只要其中某一段就复制对应的 P1–P5；想一口气走完整流程就用 P0。

## 一、原始提示词摘录（截图原文）

### 原 1｜生成 Skill

```text
请在当前项目中创建一个可以开源的 Skill：
- Skill 名称：make-knowledge-cards
- 创建位置：skills/make-knowledge-cards
- 功能：把用户粘贴的文章或本地 Markdown/TXT 文件转换成5～8张知识卡片
- 每张卡片包含：标题、核心知识、简明解释、例子或自测问题
- 要求：提取真正重要的知识；一张卡片只讲一个知识点；删除重复内容；不能编造原文没有的信息；信息不足时不要强行凑数量
- 暂不支持：网页抓取、PDF、Anki和图形界面

请使用官方初始化工具创建 Skill，完成 SKILL.md 和 agents/openai.yaml，不要添加不必要的脚本。

完成后用不同类型的文章测试，根据结果完善 Skill，并运行 quick_validate.py 验证。

在项目根目录创建简洁的 README.md，包含介绍、使用方法和输入输出示例。

先完成本地开发和测试，不要初始化 Git，也不要上传 GitHub。
```

### 原 2｜完善 README

```text
请完善项目根目录的 README.md，确保包含：
1. 项目解决什么问题
2. 主要功能
3. 安装方法
4. 使用方法
5. 输入输出示例

README 必须与项目真实功能一致。
```

### 原 3｜发布前检查

```text
请检查整个项目是否存在：
- 密码或 Token
- 个人隐私
- 本地绝对路径
- 临时文件
- 测试垃圾文件
- 不应该公开的内容

先报告检查结果，不要执行 Git 操作。
```

### 原 4｜GitHub CLI 登录

```text
请运行 gh auth status，检查 GitHub CLI 是否已经登录。

如果没有登录，请启动 gh auth login：
- 登录 GitHub.com
- 使用 HTTPS
- 通过浏览器登录
- 允许 GitHub CLI 为 Git 配置凭据

需要账号密码、验证码、二次验证或浏览器授权时暂停，让我本人完成。
不要要求我把密码或 Token 发到对话中。

授权完成后，再次运行 gh auth status。
```

## 二、比对结论与修改点

对照 `agentskills.io` 规范（Specification / Best practices / Optimizing descriptions）与
`gh` 官方手册后，这套原始提示词的**流程设计是对的**——分阶段、有自测、发布前检查、把认证交给人。
需要修的是「与规范对齐」和「覆盖度」两处：

| 原始写法 | 问题 | 修订后 |
|---|---|---|
| 未约束名称与目录一致 | 规范硬性要求 `name` 必须等于所在目录名，否则校验失败 | 明确要求两者一致 |
| 没提 `description` | `description` 是技能被**唯一**触发依据，写不好技能根本不会被调用 | 要求写成祈使句「何时使用」，覆盖用户的不同说法，≤1024 字符 |
| 没限制 `SKILL.md` 长度 | 规范建议正文 < 500 行 / ~5k tokens | 要求正文精简，长内容放 `references/` 并注明「何时读」 |
| 「不要添加不必要的脚本」 | 方向正确，但没说清何时**该**加 | 改为：同一段逻辑会被反复重写时，加 `scripts/` 并测试 |
| 依赖 `quick_validate.py` | 该脚本属于旧版 `openai/skills`（仓库已弃用），路径不保证存在 | 改用官方标准校验：`skills-ref validate` 或 `gh skill publish --dry-run` |
| 检查项只列了「密码或 Token」 | 覆盖面不足，且靠模型肉眼找不可靠 | 扩展为密钥前缀/私钥块/PII/绝对路径/垃圾文件/大文件，并提供确定性脚本 `scripts/scan_publish_ready.py` |
| 只到「gh 登录」 | 没写怎么建仓、推送、发版 | 补 `gh repo create ... --source . --push` 与 `gh skill publish --tag` |
| README 要求 | 没问题，保留 | 补充：README 只在仓库根目录，skill 目录内不要另放 README |

另有两处现实约束，务必先确认：

- `gh skill` 系列命令仍是 **preview**，随版本可能变化；
- 发布技能需要 GitHub CLI。**先跑 `gh --version` 确认它是否存在**，没有就装（见
  `publish-github.md`）；在装好之前，规范校验改用技能自带的 `scripts/validate_skill.py`
  离线完成，不要因为缺 gh 就跳过校验。

## 三、修订后的提示词模板（可直接复制）

把 `<尖括号>` 里的内容替换成你的实际信息。P1–P5 可单用，P0 是串起来的一键版。

> **两种执行纪律，别混用。** `SKILL.md` 里只有一个硬闸门（发布前检查之后）；
> 下面 P0 中「每个阶段都停下来确认」是**给想逐步盯着的用户**用的可选加强版。
> 两者冲突时，以 `SKILL.md` 的 Workflow 为准。

### P0｜一键版（推荐）

```text
我下面给一个需求，请帮我做成一个可以开源的 Skill，并在通过检查后发布到 GitHub。

需求：<把你的需求贴在这里，或指出参考文件/截图>

请严格按顺序执行，每个阶段都停下来向我汇报，等我确认后再继续下一阶段：
1. 先把需求整理成 Skill 规格：名称、用途、输入、输出、明确不做的事、硬性约束。有歧义先问我，不要猜。
2. 用官方初始化工具创建 skill；写好 SKILL.md（description 写成“何时使用”的形式，正文精简，细节放 references/），只在确有可复用逻辑时才加 scripts/。
3. 用一个真实例子自测，把实际产物贴给我看（不要只描述）。
4. 写仓库根目录的 README：解决什么问题 / 主要功能 / 安装 / 使用 / 输入输出示例。
5. 运行 scripts/scan_publish_ready.py 做发布前检查，把结果原样报告给我。
6. 【停下等我确认】确认后再初始化 git、添加 .gitignore、提交。
7. 检查 gh 是否已登录；没登录就引导我自己完成浏览器授权，不要让我把密码或 Token 发给你，也不要把凭据写进文件。
8. 创建仓库并推送；再运行 gh skill publish --dry-run 校验，通过后 gh skill publish --tag v1.0.0 发版。
9. 报告仓库地址、release 地址，以及你没能验证的部分。

不许编造功能；不许上传任何密钥、隐私、本机绝对路径或测试垃圾文件。
```

### P1｜生成 Skill

```text
请在当前项目中创建一个可以开源的 Skill：
- Skill 名称：<小写加连字符，须与目录名完全一致>
- 创建位置：skills/<skill-name>
- 功能：<一句话说明它把什么变成什么>
- 输入：<用户会给什么>
- 输出：<产出什么，格式如何>
- 必须遵守：<关键约束，例如不得编造、只提取要点>
- 明确不做：<边界，例如不抓网页、不处理 PDF>

要求：
1. 用官方初始化工具创建 Skill，生成 SKILL.md 与 agents/openai.yaml；只在确有可复用逻辑时才建 scripts/，不要添加无用文件。
2. description 写成“何时使用”的祈使句，覆盖用户可能的不同说法，控制在 1024 字符内，且不能包含 < 或 >。
3. SKILL.md 只写模型本来不知道的内容；正文尽量在 500 行以内；细节放 references/ 并注明“何时读哪个文件”。
4. 不编造；信息不足先问我，不要强行凑内容。

先完成本地开发和自测，不要初始化 Git，也不要上传 GitHub。
```

### P2｜完善 README

```text
请完善项目根目录的 README.md，确保包含：
1. 项目解决什么问题
2. 主要功能
3. 安装方法
4. 使用方法
5. 输入输出示例

README 必须与项目真实功能一致，不得夸大或编造。
README 只放仓库根目录一份；skill 目录内不要再放 README。
```

### P3｜发布前检查

```text
请检查整个项目是否存在：
- 密码、Token、API Key、私钥、.env 文件
- 个人隐私（邮箱、手机号、身份证号等）
- 本地绝对路径（C:\...、/Users/...、/home/...）
- 临时文件、日志、缓存
- 测试垃圾文件
- 其它不应公开的内容

请运行 scripts/scan_publish_ready.py <仓库根目录> 并把结果原样报告给我。
先报告，不要执行任何 Git 操作。
```

### P4｜GitHub CLI 登录

```text
请运行 gh auth status，检查 GitHub CLI 是否已经登录。

如果 gh 未安装，先告诉我，并只给出安装命令让我确认后再执行。
如果没有登录，请启动 gh auth login：登录 github.com、使用 HTTPS、通过浏览器登录、允许 GitHub CLI 为 Git 配置凭据。

需要账号密码、验证码、二次验证或浏览器授权时暂停，让我本人完成。
不要要求我把密码或 Token 发到对话中，也不要把任何凭据写进文件或命令。

授权完成后，再次运行 gh auth status 确认，并报告登录的账号。
```

### P5｜提交与发布

```text
请提交并发布这个 Skill：
1. 初始化 git（默认分支 main），添加 .gitignore，提交，提交信息要清楚。
2. 用 gh 创建仓库并推送：
   gh repo create <repo-name> --public --source . --remote origin --push --description "<一句话描述>"
3. 运行 gh skill publish --dry-run 校验是否符合 Agent Skills 规范；通过后再运行
   gh skill publish --tag v1.0.0 发版。
4. 完成后报告仓库地址与 release 地址，并确认远端内容与本地一致（例如 git ls-remote）。

任何需要授权、验证码或 2FA 的步骤都暂停，交给我本人完成。
```

## 四、附带：触发描述自测法

`description` 决定技能会不会被调用，值得单独测一轮。

1. 写约 20 条测试语句：8–10 条「应该触发」，8–10 条「不该触发」。应该触发的里面，故意混入
   **不点名领域**的说法（例如不说「skill」，只说「我想让 AI 每次都按这个流程干」）；不该触发的要用
   **近似干扰项**（词汇重叠但其实是另一件事），而不是明显无关的句子。
2. 逐条喂给已安装该技能的 agent，记录是否被调用。
3. 该触发没触发 → 把漏掉的语境关键词补进 `description`；不该触发却触发 → 收紧范围、加限定词。
4. 只保留能真正改变触发行为的措辞，避免把 `description` 写成功能清单。
